Reader layouts

Six working reading screens on the same real poems, driven by one shared engine, so a comparison isolates layout. Every option keeps vertical swipe between poems, the word-by-word reveal, Next Verse, the progress scrubber, the reader actions, the bottom nav, and data-owns-gesture. Measured on iPhone 16 (393×852). Add ?clean to hide the probe, ?poem=0..3 to pin a length, ?reveal=all to land fully revealed.

The measurement that motivated this

On iPhone 16 the shipping reader gives the poem a 305px-wide box out of 393px, and only 8 verse rows fit between the header and the action bar. The Arabic is already being shrunk (--fit 0.98) to survive that width. On landing it is far worse: one verse is revealed inside a window that reserves blank rows for the rest, so 555px of the screen is held open and empty.

Correction — the first numbers were Arabic-only

The reader is bilingual by default (showTranslation = true), and SparklerStage sizes rows by the tallest unit — so a translated verse is a tall row. The first cut of this folder measured Arabic-only rows and reported 8 verses for the shipping reader. Corrected, it fits 4 bilingual verses of a 22-line qasida. Only ~13% of the corpus carries a translation (the API's english is hardcoded ''; real ones arrive as cachedTranslation), which is how the error stayed invisible. Add ?lang=ar or ?lang=translit to any option to see the other two states.
